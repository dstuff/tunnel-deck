# Реализация VPN-протоколов в TunnelDeck

Состояние реализации: 17 октября 2026 года. Документ описывает текущий код
приложения и результаты зафиксированных проверок. При изменении кода необходимо
обновлять соответствующие разделы и сведения о проверках.

## 1. Общая архитектура

TunnelDeck — SwiftPM-приложение для macOS 14+ с двумя исполняемыми файлами:
`TunnelDeck` и `TunnelDeckHelper`. Поставляемые двоичные движки рассчитаны
на Apple Silicon. UI работает от имени пользователя; настройку интерфейсов,
маршрутов и DNS выполняет отдельный helper с правами администратора.

Криптографию и обмен с VPN-серверами выполняют профильные движки. Swift-код
импортирует настройки, готовит конфигурацию, управляет процессами и сетью,
проверяет готовность и отображает состояние.

| Протокол в приложении | Движок | Путь трафика | Условие состояния «Подключено» |
| --- | --- | --- | --- |
| OpenConnect / ocserv | OpenConnect 9.21 + OpenSSL 3.6.2; общий Xray/Hev | Общий TUN → маршрутизатор → scoped-интерфейс OpenConnect → ocserv | Cookie авторизации, проверенные параметры сети и запуск общей маршрутизации |
| AmneziaWG 3.1 | `amneziawg-go` 3.1.20260828, `awg-tools` 3.1.20260812; общий Xray/Hev | Общий TUN → маршрутизатор → scoped-интерфейс AWG → сервер | Установлена сеть и получен ненулевой timestamp handshake хотя бы одного Peer |
| Xray | Xray 26.3.27+tunneldeck.4, HevSocks5Tunnel 2.19.0 | `utun` → Hev/lwIP → локальный SOCKS5 → Xray → сервер | После установки сети получен успешный HTTPS-ответ через системный туннель |

Реальные версии, источники и SHA-256 находятся в
[Runtime/versions.json](../Runtime/versions.json). Версия в исторической строке
`--version` движка AWG может отличаться от тега исходников; для определения
поставляемой версии следует использовать manifest и закреплённый источник.

### 1.1. Управление сеансом и права

Основная логика UI находится в
[ConnectionController.swift](../Sources/TunnelDeck/Services/ConnectionController.swift).
Один экземпляр приложения управляет одним подключением; helper дополнительно
получает эксклюзивную блокировку `/var/run/tunneldeck.lock`.

Порядок подключения:

1. Прочитать и проверить профиль, убедиться в наличии движка.
2. Для OpenConnect отдельно получить cookie авторизации от имени пользователя.
3. Создать приватный каталог сеанса и передать helper структурированный запрос.
4. Через стандартный запрос macOS запустить поставляемый helper с правами root.
5. Запустить нужный backend, настроить сеть и получать события из `events.jsonl`.
6. Перейти в «Подключено» по критерию конкретного протокола, указанному в таблице.

Передача запроса реализована в
[PrivateSession.swift](../Sources/TunnelCore/PrivateSession.swift) и
[SecureSession.swift](../Sources/TunnelDeckHelper/SecureSession.swift):

- каталог сеанса имеет права `0700`, файлы и управляющий FIFO — `0600`;
- UI и helper удерживают разделяемую блокировку файла `lease` до завершения
  работы с каталогом; очистка получает исключительную неблокирующую блокировку;
- helper проверяет владельца, права, тип файлов, отсутствие символических ссылок
  и лишних жёстких ссылок; размер запроса ограничен 512 000 байт;
- запрос содержит UID пользователя и PID UI; после чтения `request.json` удаляется;
- команда отключения передаётся через FIFO `control`;
- helper отслеживает существование родительского процесса и обрабатывает
  `SIGINT`/`SIGTERM`;
- временные рабочие конфигурации создаются в отдельном root-каталоге с правами
  `0700` и удаляются при штатном завершении backend.

Запуск процессов и их остановка описаны в
[ChildProcess.swift](../Sources/TunnelDeckHelper/ChildProcess.swift).
После мягкой остановки предусмотрена эскалация до принудительного завершения
дочернего движка. Это управление дочерними процессами не означает гарантированную
очистку сети при `SIGKILL` самого helper или аварии ОС.

Журнал сеанса ограничен **5 000 000 байтами**, включая служебные записи.
[SessionEventLog.swift](../Sources/TunnelCore/SessionEventLog.swift) при достижении
лимита очищает старые диагностические сообщения и продолжает запись в тот же
проверенный файл. В нём сохраняется последнее событие каждого служебного типа,
в том числе готовность сети, ошибка и завершение. Большие отдельные сообщения
сокращаются; JSON-экранирование также учитывается в размере записи. Секреты
скрываются до сокращения и записи сообщения, включая параметры и вложенные ошибки
локализуемых сообщений. Нейтральные маркеры `<redacted>` не зависят от языка UI.

`TunnelEvent` дополнительно содержит необязательный `localizedMessage` — ключ,
типизированные параметры и запасной текст. Helper передаёт собственные сообщения
структурированными, а `message` сохраняет совместимый английский текст. Исходный
вывод движков остаётся строками. UI хранит дескрипторы и переводит их при показе
и копировании, поэтому смена языка обновляет уже накопленную историю. Старые
события, неизвестные ключи и неподдерживаемые дескрипторы используют `message`;
тип события и сетевой жизненный цикл от языка не зависят. Ошибочные типы аргументов
не передаются в форматирование C varargs. Лимит записи учитывает весь JSON;
если дескриптор не помещается, сохраняется сокращённый строковый текст.

Чтение и запись согласованы файловой блокировкой. Заголовок поколения и
порядковые номера позволяют UI продолжить чтение после очистки файла без
повторной обработки уже полученных событий. В окне остаются последние
1200 записей; кнопка очистки очищает только этот список в памяти.

При запуске UI удаляет оставшиеся каталоги сеансов текущего пользователя,
если ни UI, ни helper больше не удерживают их `lease`. Проверяются имя UUID,
права и владелец; символические ссылки и каталоги прежних версий без `lease`
не удаляются. При штатном завершении каталог удаляется сразу, как и раньше.

Главное окно показывает компактный список профилей. «Переключиться» управляется
[ProfileSwitcher.swift](../Sources/TunnelDeck/Services/ProfileSwitcher.swift):
сначала вызывается штатное отключение, затем ожидается снятие блокировки
контроллера и состояние `idle`. Для сеанса с helper это происходит после события
`stopped`, которым подтверждается завершение его очистки. Только после этого
загружается выбранный профиль и запускается новое подключение. Повторные нажатия
не создают дополнительные операции. При ошибке, отмене или ожидании дольше
30 секунд следующий туннель не запускается; таймаут не прерывает восстановление
сети. Отмена операции до запуска helper также сохраняет блокировку до завершения
её задачи, чтобы новая авторизация не пересеклась с отменённой.

Добавление и редактирование разрешены при установившемся подключении; изменения
профиля относятся к следующему запуску, а текущий helper использует полученный
снимок настроек. Удалять активный профиль нельзя. Во время переходных состояний
редактирование и добавление временно недоступны. Закрытие главного окна сохраняет
сеанс и доступ через строку меню; выход из приложения отменяет отложенное
переключение и запускает обычное отключение.

### 1.2. Секреты и профили

Все данные профилей хранятся локально в
`~/Library/Application Support/TunnelDeck/profiles.json`: названия, адреса,
параметры протоколов, пароли, camouflage, исходные конфигурации AWG/Xray,
незавершённый ввод сервера и выбранный профиль. JSON-документ версии 3 содержит общую схему `routing`,
`profiles`, `selectedProfile` и словарь `secrets` с UUID профилей в качестве
строковых ключей. Разделение метаданных и секретов в моделях и запросах helper
сохраняется, но на диске они записываются одним документом.

Дополнительного шифрования файла нет. Каталог имеет права `0700`, файл и
временные файлы записи — `0600`. Запись выполняется в приватный временный файл
с последующей атомарной заменой; при ошибке временный файл удаляется. Приложение
не обращается к Связке ключей. Все поля сохраняются автоматически через 350 мс
после редактирования, а также при переключении профиля и выходе; переключателя
сохранения секретов нет. Cookie авторизации остаются временными данными сеанса.

Автосохранение и совместимость со старыми форматами реализованы в
[AppModel.swift](../Sources/TunnelDeck/Stores/AppModel.swift) и
[ProfileStore.swift](../Sources/TunnelDeck/Stores/ProfileStore.swift).
Старый массив профилей и документ с метаданными читаются с сохранением UUID,
порядка и выбора; секреты из прежней Связки ключей не переносятся и вводятся
повторно. Старый признак отказа от сохранения секретов игнорируется. Обновлённый
формат записывается при следующем успешном сохранении.

Отсутствующий файл считается первым запуском: создаётся начальный профиль
«Мой ocserv» / «My ocserv» на выбранном языке. Его можно удалить, в том числе если он единственный. Пустой список
сохраняется с отсутствующим `selectedProfile` и пустым `secrets`; при следующем
запуске, автосохранении и выходе начальный профиль не создаётся заново.
Общие правила маршрутизации сохраняются и без подключений. В пустом списке
доступно добавление и импорт; проверка и запуск VPN требуют выбранного профиля.

Ошибка чтения, повреждённый или
неподдерживаемый формат показываются пользователю и блокируют запись до
исправления файла и перезапуска приложения, чтобы исходные данные не затирались.
Ошибка записи сохраняет текущие правки и прежний документ; неудачные добавление,
импорт, удаление и смена выбора не создают частичных изменений списка профилей.
[LogRedactor.swift](../Sources/TunnelCore/LogRedactor.swift) скрывает известные
секреты и чувствительные шаблоны перед записью событий helper, показом и экспортом
журнала. Рабочие профили пользователей не являются тестовыми примерами.

Окно «Добавить подключение» использует
[ConnectionImport.swift](../Sources/TunnelDeck/Models/ConnectionImport.swift):
по тексту или файлу определяется OpenConnect, AWG `.conf`, JSON Xray либо
VLESS/Trojan-ссылка. Используются те же парсеры и ограничения, что и в редакторе;
camouflage отделяется от метаданных внутри модели, исходная приватная конфигурация
сохраняется целиком в локальном документе. Ошибка записи не добавляет частичный
профиль. Распознавание формата не подтверждает handshake или передачу данных.
По умолчанию импорт
не подключает VPN; это можно явно включить перед добавлением.

### 1.3. Общая схема маршрутизации и файлы обмена

Все подключения используют одну схему `RoutingPolicy` из локального документа.
Миграция версий 1/2 сохраняет профили, UUID и секреты и добавляет схему без правил
с действием по умолчанию «Через VPN». Незаконченные правки правил сохраняются
локально, но не допускаются к подключению, применению и экспорту до исправления.
Ошибка чтения/версии по-прежнему блокирует запись исходного документа.

Окно «Маршрутизация» открывается из главного окна, настроек, строки меню или
Command-Option-R. Слева находится единый упорядоченный список, справа — редактор.
Поддерживаются точный домен, домен с поддоменами, IPv4/IPv6-адрес или подсеть,
страна IP по поставляемой базе. Действия: `vpn`, `direct`, `block`.
Первое включённое совпадение определяет маршрут; при отсутствии совпадений
используется `defaultAction` (`vpn` или `direct`). Сайты нормализуются в нижний
регистр/IDNA; поддомен сопоставляется по границе метки, URL означает весь сайт.
Компилятор добавляет варианты домена с завершающей DNS-точкой и без неё:
`2ip.io` и `2ip.io.` обозначают один сайт, включая восстановление из FakeDNS.
Страна определяется по IP, а не языку или доменной зоне. Для домена IP-правила,
включая GeoIP, используют результаты DNS согласно семантике Xray IPOnDemand.

Активный helper использует неизменяемый снимок схемы в `TunnelRequest`.
Редактирование не меняет текущий сеанс; «Применить и переподключить» использует
существующий ProfileSwitcher и ждёт подтверждённой очистки предыдущего helper.
При ошибке валидации/сохранения переподключение не запускается. Импорт не запускает
подключение и требует просмотра списка перед полной заменой схемы.

Файл `.tunneldeck-routing` — автономный JSON версии 1. Он содержит только
`format`, `version`, `name`, `defaultAction`, `rules`; правило — `id`, `match`
(`type`, `value`), `action`, `enabled`. UUID/`enabled` необязательны при импорте.
Неизвестные поля, версии, условия и действия отклоняются целиком. Ограничения:
128 000 байт и 1000 правил; запрос профиля вместе со схемой — максимум 512 000
байт с учётом JSON-экранирования. Данные подключений и секреты в экспорт не входят.

```json
{
  "format": "tunneldeck-routing",
  "version": 1,
  "name": "Пример",
  "defaultAction": "vpn",
  "rules": [
    {"match": {"type": "domainSuffix", "value": "example.org"}, "action": "direct"},
    {"match": {"type": "country", "value": "RU"}, "action": "direct"}
  ]
}
```

В Xray-профиле с несколькими серверными outbounds требуется выбор основного
`xrayOutboundTag`. В рабочую конфигурацию попадают выбранный транспорт и его
явные зависимости через `proxySettings.tag`/`sockopt.dialerProxy`. Отсутствующие
ссылки и циклы отклоняются. Исходный JSON сохраняется, но его `routing`, `dns`,
`policy` и слушатели не управляют общей рабочей схемой. Кнопка «Проверить» также
использует выбранный сервер, отдельно от пользовательских правил.

### 1.4. Язык интерфейса и ресурсов

`TunnelLocalization` — общий модуль Foundation/Observation для приложения,
TunnelCore и helper. Поддерживаются только `ru` и `en-US`; ресурсы `.strings`,
`.stringsdict` и `InfoPlist.strings` находятся в соответствующих `.lproj`.
`defaultLocalization` и `CFBundleDevelopmentRegion` равны `en-US`.

Настройка `appLanguage` хранится в UserDefaults со значениями `system`, `ru`,
`en-US`, отдельно от профилей и секретов. В системном режиме используется только
первый язык `Locale.preferredLanguages`: русский вариант даёт `ru`, любой другой
(включая `en-GB` или список `de, ru`) — `en-US`. Уведомление об изменении локали
повторно вычисляет язык. Смена переводит собственные окна, меню, ошибки и журнал,
сохраняя состояние SwiftUI и VPN-сеанс. Пользовательские имена не переписываются;
новые стандартные названия создаются на текущем языке. Названия стран и сортировка
используют язык приложения; форматы времени сохраняют системную локаль.
Системные диалоги и сторонний вывод остаются под управлением macOS/движков.

Скрипт упаковки копирует `TunnelDeck_TunnelLocalization.bundle` в
`Contents/Resources`, а `InfoPlist.strings` — в локализации основного приложения.
Модуль находит ресурсы и из `Contents/MacOS`, и из `Contents/Helpers`; при обычном
запуске SwiftPM используется `Bundle.module`. Ресурсы входят в подпись приложения.

## 2. OpenConnect / ocserv

### 2.1. Компоненты и конфигурация

Формирование параметров находится в
[OpenConnectConfiguration.swift](../Sources/TunnelCore/OpenConnectConfiguration.swift),
запуск туннеля — в `BackendRunner.openConnect()` файла
[Backends.swift](../Sources/TunnelDeckHelper/Backends.swift).

Используется протокол OpenConnect `anyconnect`. CSTP поверх TLS и DTLS при
возможности его использования обрабатывает сам OpenConnect. Поле профиля
`disableDTLS` добавляет `no-dtls`.

Поле сервера принимает полный HTTPS URL, включая путь и camouflage после `?`.
`VPNEndpoint` сохраняет точное значение query, включая percent-encoding, и
передаёт его в `server=`. Если схема отсутствует, добавляется `https://`.
HTTP, user/password в URL, фрагмент `#` и управляющие символы отклоняются.

Camouflage не превращается в `authgroup`. Для старых профилей допускается
отдельное значение camouflage; если оно конфликтует с query URL, конфигурация
отклоняется. Логин, группа и pin сертификата проверяются на перевод строки
и NUL. Pin должен начинаться с `pin-sha256:` или `sha256:`.

Сгенерированная конфигурация содержит `protocol=anyconnect`, точный `server=`,
`non-inter`, `no-proxy`, а при наличии — `user=`, `authgroup=`, `servercert=`.
Проверка сертификата по умолчанию включена.

### 2.2. Проверка и подключение

Кнопка «Проверить» выполняет HTTPS-запрос без изменения маршрутов и без входа
с паролем. Ожидается HTTP 200 и ответ, похожий на форму AnyConnect/ocserv.
Используется системная проверка TLS через URLSession; pin из профиля применяется
в командной конфигурации OpenConnect при авторизации, а не этой URLSession-пробой.

При подключении выполняются две стадии:

1. UI запускает OpenConnect с `--cookieonly --passwd-on-stdin`. Пароль передаётся
   через stdin, конфигурация — приватным файлом. Успехом считается код возврата 0
   и ровно одна непустая строка cookie размером до 64 000 байт.
2. Из запроса helper удаляется пароль авторизации. Helper запускает OpenConnect
   с `--cookie-on-stdin`, `--verbose`, `--script` и `--reconnect-timeout=30`.
   Cookie передаётся через stdin, а не аргументом процесса.

Наличие cookie подтверждает авторизацию; рабочую сеть подтверждает следующая
стадия сетевого скрипта.

### 2.3. Маршруты, DNS и завершение

OpenConnect запускается с поставляемым helper в качестве `--script`:
`--openconnect-network <root-scratch>`. Callback не запускает команды из
конфигурации сервера и не вызывает `vpnc-script`. Он проверяет `reason`, имя
`utun`, числовые адреса, MTU, DNS и split include/exclude (не более 256 на список),
затем атомарно записывает только эту метаинформацию в закрытый root-каталог.
Права каталога и тип файла проверяются; cookie и переменные окружения целиком
в событие не записываются. Бинарник и штатный vpnc-script остаются закреплёнными
компонентами сборки; автоматического перехода к чужому скрипту/Homebrew нет.

Основной helper применяет адреса/MTU и scoped-маршруты транспорта, запрещающие
split exclude, затем запускает общий маршрутизатор и TUN-мост. После этого
публикуется `connected`; отдельная HTTPS-проверка проверяет VPN и системный TUN,
но её неудача не подменяет статус авторизации/готовности сети OpenConnect.
`attempt-reconnect` переводит UI в восстановление; существующие правила остаются
включены до получения новых параметров. При `reconnect` общий путь пересоздаётся
с новым снимком сетевых параметров и прежней пользовательской схемой.
Восстановление ограничено 60 секундами.

При остановке восстанавливаются собственные маршруты и DNS, затем останавливаются
общий мост/маршрутизатор и OpenConnect. OpenConnect освобождает свой интерфейс.
Обработчик `disconnect` сам не меняет глобальные маршруты.

### 2.4. Автономная сборка и перенос

[script/build_openconnect.sh](../script/build_openconnect.sh) собирает отдельный
клиент из неизменённых исходников OpenConnect 9.21 со статическими библиотеками
OpenSSL 3.6.2. Для сборки pkgconf 3.0.8 также собирается из закреплённого архива
в приватном рабочем каталоге проекта; установка build tools через Homebrew
не требуется. Все архивы и vpnc-script фиксированы SHA-256, источник скрипта —
commit `ce9e961bd0f6b867e1c7c35f78f6fb973f6ff101`. Версии, ссылки на исходники,
SHA-256 движка и build script записываются в `Runtime/versions.json`.

Целевая архитектура — arm64, минимальная версия — macOS 14.0. OpenSSL включён
статически, внешние providers/DSO отключены. Из динамических зависимостей
разрешены только Apple `/usr/lib` и `/System/Library`. Проверка
[script/verify_openconnect.py](../script/verify_openconnect.py) отклоняет
сторонние dylib, другую архитектуру, повышение deployment target или неожиданную
версию OpenConnect/OpenSSL; она выполняется перед упаковкой. В bundle входят
лицензии, уведомление о составе и скрипты пересборки.

TLS/DTLS теперь использует OpenSSL вместо GnuTLS установленного ранее
Homebrew-клиента. Проверка сертификата включена; OpenSSL собран с
`--openssldir=/etc/ssl` и использует системный `/etc/ssl/cert.pem`. Это не
автоматический импорт пользовательских сертификатов из Связки ключей.
Явный `servercert` по-прежнему передаётся движку. PKCS#11, SecurID, аппаратный
Yubikey, GSSAPI и LZ4 в этой сборке не включены; приложение использует
логин/пароль, cookie, CSTP и при доступности DTLS.

ocserv остаётся на удалённом сервере: в приложение включён клиент OpenConnect,
серверный демон не требуется. На другом Mac не нужны Homebrew и отдельная
установка OpenConnect. Сборка остаётся локальной ad-hoc и не заверена Apple.
Deployment target и отсутствие сторонних dylib не заменяют запуск на macOS 14
или отдельном чистом Mac; эти варианты требуют самостоятельной проверки.

## 3. AmneziaWG 3.1

### 3.1. Импорт `.conf`

Парсер находится в
[AmneziaConfiguration.swift](../Sources/TunnelCore/AmneziaConfiguration.swift),
подключение — в `BackendRunner.amnezia()` файла
[Backends.swift](../Sources/TunnelDeckHelper/Backends.swift).

Разделы `[Interface]` и `[Peer]` разбираются в строгом формате; комментарии
после `#` удаляются. Размер текста должен быть меньше 256 000 байт.
Нужны приватный ключ, адрес интерфейса, Peer с публичным ключом и Endpoint
в конфигурации. Ключи проверяются как Base64 от 32 байт; IP, CIDR и порт
Endpoint проходят отдельную валидацию.

| Категория | Обработка |
| --- | --- |
| `Address`, `DNS`, `MTU`, `Table` | Извлекаются из конфигурации движка; применяются helper |
| `PrivateKey`, `ListenPort`, `FwMark` | Передаются движку |
| `Jc`, `Jmin`, `Jmax`, `S1`–`S4`, `H1`–`H4`, `I1`–`I5` | Сохраняются и передаются официальным инструментам AWG |
| `HeaderProtectionKey`, `ContentPaddingAddition` | Сохраняются; для включённого HeaderProtectionKey дополнительно требуются `S1`–`S4` не меньше 12 |
| `RekeyAfterTime`, `RekeyTimeout`, `RejectAfterTime`, `KeepAliveTimeout`, `MaxHandshakeAttempts`, `RandomTrailers`, `DisableCookies` | Сохраняются; семантику проверяет движок |
| Peer: `PublicKey`, `PresharedKey`, `Endpoint`, `AllowedIPs`, `PersistentKeepalive` | Сохраняются, включая поддерживаемые движком диапазоны значений |
| `PreUp`, `PostUp`, `PreDown`, `PostDown`, `SaveConfig` | Отклоняются |

Неизвестные поля отклоняются. MTU по умолчанию — 1420; допустимый диапазон
импортера — 1280–9000. Для `Table` поддерживаются только `auto` и `off`.
`Table` сохраняется в исходном профиле. В общем режиме маршрутизации helper
всегда создаёт scoped-маршруты к AllowedIPs для сокетов VPN-канала; `Table=off`
не отключает пользовательскую схему и не устанавливает глобальные маршруты AWG.
AllowedIPs не расширяется: адреса вне покрытия Peer не получают обход напрямую.

### 3.2. Запуск и настройка сети

1. Helper записывает очищенную device-конфигурацию в приватный `awg.conf`.
2. Запускает `amneziawg-go -f utun`, задавая `WG_TUN_NAME_FILE` и `LOG_LEVEL=error`.
3. До 10 секунд ждёт файл с корректным именем `utunN`.
4. Передаёт конфигурацию через `awg setconf`.
5. Добавляет исключения для серверных Endpoint через исходный шлюз.
6. Применяет адреса/MTU и scoped AllowedIPs через `NetworkConfiguration`.
7. Запускает общий Xray/Hev, который применяет глобальную схему и DNS ко всем
   захваченным потокам, а VPN-направление привязывает к интерфейсу AWG.

Сама реализация AWG, шифрование, handshake и поля обфускации находятся в
закреплённых исходниках `amneziawg-go` и `amneziawg-tools`.

### 3.3. Готовность и остановка

Кнопка «Проверить» проверяет структуру и извлечённые параметры `.conf`;
пакеты серверу не отправляются.

После настройки сети helper раз в две секунды вызывает
`awg show <interface> latest-handshakes`. Первый ненулевой timestamp хотя бы
одного Peer подтверждает подключение. Это не проверка всех Peer. При отсутствии
первого handshake более 45 секунд сеанс завершается с ошибкой.

После handshake UI дополнительно проверяет HTTPS. Неудачный запрос фиксируется
в журнале, но не отменяет статус handshake и не запускает автоматическое
отключение по правилам Xray. Непрерывная оценка свежести последующих handshake
и периодическая HTTPS-проверка не реализованы.

Штатная остановка завершает движок и удаляет установленные этим сеансом маршруты
и временный DNS. Интерфейс освобождается после остановки движка.

## 4. Xray и поддерживаемые proxy-протоколы

### 4.1. Импорт и границы поддержки

Импорт и генерация конфигурации находятся в
[XrayConfiguration.swift](../Sources/TunnelCore/XrayConfiguration.swift).
Схема системного туннеля описана в
[SocksTunnelConfiguration.swift](../Sources/TunnelCore/SocksTunnelConfiguration.swift),
запуск — в `BackendRunner.xray()` файла
[Backends.swift](../Sources/TunnelDeckHelper/Backends.swift).

| Входной формат | Что принимает приложение |
| --- | --- |
| `vless://` | UUID/identity, сервер, порт, encryption, flow, параметры транспорта и TLS/REALITY |
| `trojan://` | Пароль в user-части URI, сервер, порт и параметры транспорта; TLS по умолчанию |
| JSON с `outbounds` | Перечень исходящих подключений и разрешённые верхнеуровневые настройки |
| JSON отдельного outbound | Оборачивается в массив `outbounds` |

Whitelist outbound-протоколов импортера: `vless`, `vmess`, `trojan`,
`shadowsocks`, `socks`, `http`, `freedom`, `blackhole`, `dns`, `wireguard`,
`hysteria`. Их wire-реализация делегирована Xray core. Наличие имени в whitelist
не означает, что каждый вариант протокола и его системная маршрутизация проверены
на реальном сервере. VMess/Shadowsocks и другие URI, кроме VLESS/Trojan,
этот импортер не разбирает — для них нужен JSON.

Для VLESS/Trojan-ссылок поддерживаются `tcp`/`raw`, `ws`, `grpc`, `xhttp`,
`httpupgrade`. `tcp` нормализуется в `raw`. Параметры `path`, `host`,
`serviceName`, `mode`, `sni`/`peer`, `fp`, `pbk`, `sid`, `spx` раскладываются
в соответствующие настройки core. Для REALITY необходим публичный ключ;
сочетания REALITY с WS/HTTPUpgrade импортер отклоняет.

Параметр ссылки `alpn` переносится только в обычный `tlsSettings`, не в
`realitySettings`. Ссылки с `allowInsecure=1` или `true` отклоняются. Это правило
импорта ссылок не является полной проверкой TLS-политики произвольного JSON.

Исходный JSON, включая `outbounds`, `routing`, `dns`, `policy`, сохраняется локально.
В рабочий общий маршрутизатор передаётся выбранный outbound с его зависимостями;
маршрутизация, DNS и policy задаются TunnelDeck.
Пользовательские `inbounds`, `api` и назначения журналов не запускаются;
слушатель и журнал задаёт приложение. Запрещённые поля ссылок на внешние
сертификаты, ключи, key log, файлы и скрипты проверяются рекурсивно.
Размер импортируемого текста должен быть меньше 256 000 байт.

### 4.2. Общий путь TCP/UDP и локальные слушатели

```text
Приложения macOS → capture-маршруты → utun → Hev/lwIP → SOCKS5 td-traffic → Xray
  → td-vpn: выбранный Xray outbound ИЛИ Freedom с привязкой к utun OpenConnect/AWG
  → td-direct: Freedom с привязкой к исходному физическому интерфейсу
  → td-block: Blackhole
```

Hev использует обычный SOCKS5 UDP relay; его YAML генерирует TunnelDeck.
Интерфейс выбирается среди свободных utun300–utun999, MTU 4064,
адреса `198.18.0.1/24`, `fd00:1234:ffff::10/64`. ICMP echo выключен.
Старые генераторы `data(tunnelInterface:)`/`proxyData` остаются для совместимости
и тестов, но рабочий `Connect` использует `RoutingConfiguration`.

Все слушатели Xray привязаны к 127.0.0.1 и динамическим разным портам:
`td-traffic` для Hev, `td-probe` для проверки VPN, `td-dns-real` для объяснения
правил без FakeDNS и `td-system-probe` для проверки системного пути.
Порты проверки передаются UI типизированным событием `routingReady`.
Служебные маршруты DNS/проб имеют приоритет над пользовательскими правилами.

### 4.3. Порядок запуска Xray

1. Сохранить физический интерфейс, шлюзы и DNS до захвата трафика.
2. Разрешить серверные hostname через getaddrinfo(AF_UNSPEC), выбрать первый
   адрес, сохранить исходный hostname в SNI при его отсутствии. Endpoint discovery
   охватывает vnext, servers, Hysteria address и WireGuard peers.endpoint.
3. Добавить обходные маршруты к серверным IP, сформировать общий JSON и YAML Hev.
4. Проверить JSON настоящим `xray run -test`; запустить Xray и дождаться слушателей.
5. Запустить Hev, дождаться обоих адресов интерфейса и флага UP.
6. Применить capture IPv4/IPv6 и общий DNS; отправить `routingReady`/`networkReady`.
7. Проверить HTTPS через принудительное VPN-направление и через системный TUN.
   Только после обеих успешных проверок Xray получает состояние «Подключено».

Сокеты серверных зависимостей принудительно используют исходный интерфейс;
ссылки цепочки переписываются в пространство тегов TunnelDeck. Автоматического
sendThrough на физический IPv4 нет. Исходные параметры криптографии и TLS
сохраняются с описанным ниже преобразованием профиля совместимости.

### 4.4. REALITY / XTLS Vision и TLS-профиль совместимости

В поставляемом Xray добавлен отдельный профиль `tunneldeck_safari15_5`.
Он строится на публичном uTLS Safari 16 preset со следующими изменениями:

- из списка расширений удаляется ALPN;
- из списка алгоритмов подписи удаляется повторный `RSA-PSS/SHA384`;
- сохраняются обычный X25519 key share и остальные параметры базового preset.

Это воспроизводит параметры совместимого профиля Safari 15.5. Побайтовое
совпадение с сериализацией BoringSSL и нативное поведение TCP не заявляются.

Автоматический выбор профиля в генераторе применяется только при всех условиях:

1. Outbound — `vless`, защита — `reality`.
2. Хотя бы один user в `vnext` имеет `flow`, начинающийся с `xtls-rprx-vision`.
3. Исходный fingerprint отсутствует/пустой либо равен `chrome`, `safari`,
   `safari15_5`, `tunneldeck_safari15_5`.

Тогда в runtime JSON fingerprint становится `tunneldeck_safari15_5`.
Другие явно заданные профили, например `hellochrome_131` и `firefox`, остаются
как указаны пользователем. Исходный сохранённый JSON не переписывается;
ключи, SNI, short ID и flow этим преобразованием не изменяются.

Patch изменяет выбор и построение ClientHello, сохраняя механизм REALITY
authentication, проверку сертификата и числовую версию клиента `26.3.27`.
Сборка явно обозначена `TunnelDeck.4` и не выдаётся за неизменённый upstream.
Имя профиля согласовано в генераторе, core patch, тестах и поставляемом движке.
В журнале проверки и helper используется локализуемое сообщение
«REALITY/Vision: используем TLS-профиль совместимости TunnelDeck.»
(на английском — «REALITY/Vision: using the TunnelDeck compatibility TLS profile.»).
Фрагментация TLS, ограничение числа handshake и подмена на стандартный Safari
не включены автоматически: проведённые эксперименты не подтвердили их как
устойчивое исправление.

Исходный patch и воспроизводимая сборка:

- [script/xray_compat.patch](../script/xray_compat.patch);
- [script/build_xray_compat.sh](../script/build_xray_compat.sh);
- [уведомление о модификациях и лицензии](../Runtime/licenses/Xray-compat-notice.txt).

### 4.5. Проверка и завершение

«Проверить» запускает `xray run -test` и SOCKS-проверку выбранного серверного
outbound: один HTTPS-запрос, затем восемь параллельно. TUN, маршруты и DNS этой
проверкой не меняются.

При подключении сначала выполняется HTTPS через `td-probe` с принудительным
`td-vpn`. Затем curl выполняет HTTPS example.com с `--resolve` на служебный
`198.18.0.3`: запрос проходит системные маршруты → Hev → td-traffic → служебный
loopback-мост → td-system-probe → td-vpn. TLS проверяется для настоящего имени
example.com. В `TunnelDeck.4` dispatcher сохраняет исходное назначение только
для TCP `198.18.0.3:443` на `td-traffic`: HTTP Host/TLS SNI этой пробы не подменяет
цель маршрутизации. Иначе `routeOnly` вместе с `IPOnDemand` разрешает распознанное
имя и IP-условие служебного моста перестаёт совпадать. Для остальных адресов,
портов, протоколов и inbound поведение sniffing/DNS сохраняется.
Пользовательское исключение/блокировка example.com не может сделать
эту проверку прямой или заблокировать служебный путь. Лимит каждого запроса —
15 секунд. Неудача стартовой проверки Xray останавливает helper и восстанавливает
сеть. Для OpenConnect/AWG она фиксируется отдельно от авторизации/handshake.

Очистка: восстановить собственные маршруты и DNS, остановить Hev и Xray, затем
нативный транспорт. Helper следит за работой движков на всём протяжении сеанса.

## 5. Общая маршрутизация и DNS

`NetworkConfiguration` управляет одной транзакцией сети для всех backend.
Глобальный default route сохраняется; capture использует `0.0.0.0/1`,
`128.0.0.0/1`, `::/1`, `8000::/1`. Маршруты native OpenConnect/AWG имеют
`-ifscope utunN`: они доступны привязанным VPN-сокетам, но не подменяют общий
выбор маршрута. Split exclude OpenConnect добавляется как scoped reject.
Существовавшие host-маршруты не считаются созданными этим сеансом и не удаляются.

Перед каждым capture-префиксом helper устанавливает такой же префикс
с `-ifscope` исходного физического интерфейса через сохранённый шлюз.
Он нужен сокетам `td-direct` и серверных Xray-outbound с `IP_BOUND_IF`:
после установки более специфичных capture-маршрутов одного глобального
физического default route недостаточно, и Darwin может вернуть
`network is unreachable`. Scoped-префиксы не меняют выбор пути обычных
непривязанных приложений. Для IPv6 используется только исходный default
того же физического интерфейса; шлюз другого `utun` не переносится на него.
On-link default сохраняется как `-interface`. Эти маршруты входят в ту же
транзакцию, удаляются в обратном порядке после capture-маршрутов; уже
существовавшие scoped-префиксы остаются после отключения.

Системный DNS временно задаётся через SCDynamicStore: `198.18.0.2`, пустой
SupplementalMatchDomains. TCP/UDP 53 из td-traffic попадает в общий DNS-outbound.
FakeDNS выдаёт адреса из `198.19.0.0/16` и `2001:2::/48`, TTL 1 секунда.
Входящие TCP/UDP-потоки восстанавливают DNS-идентичность. Если FakeDNS не знает
реальный IP (например, Chrome использует свой DNS или сохранённый ответ),
маршрутизатор дополнительно распознаёт HTTP Host, TLS SNI и QUIC. Для реальных
IP включён `routeOnly`: имя выбирает правило, IP назначения остаётся исходным.
Известная FakeDNS-идентичность имеет приоритет над Host/SNI и по-прежнему
заменяет синтетический IP настоящим именем для подключения. Домен, полученный
из DNS, может иметь завершающую точку: Xray routing сопоставляет её буквально,
поэтому точные и suffix-правила явно включают обе формы имени. Порядок правил
остаётся прежним. Когда имя не видно (например, ECH без известной FakeDNS-записи
или произвольный UDP), используются IP/страны/действие по умолчанию.

Реальный DNS для Freedom/GeoIP пропускает FakeDNS. Для явно заданных доменных
правил используются резолверы соответствующего направления; для остальных —
направления по умолчанию. При наличии DNS от native VPN используются они,
иначе 1.1.1.1/8.8.8.8; для прямого направления берётся исходный DNS физической
службы с тем же резервом. Переключения между VPN/прямым DNS при ошибке нет.

Для Freedom, привязанного к native OpenConnect/AWG, семейство адресов домена
выбирается по назначенным адресам профиля/события сервера. Только IPv4 означает
`ForceIPv4`, только IPv6 — `ForceIPv6`, оба семейства — `UseIP`. Автоматический
link-local IPv6 не считается поддержкой IPv6 для выхода в интернет; одного
`AllowedIPs = ::/0` недостаточно. Это предотвращает попытки подключиться к AAAA
через IPv4-only VPN. Literal IPv6 не преобразуется в IPv4; серверные возможности
и AllowedIPs не расширяются. Для выбранного Xray-outbound сохраняются его
собственные настройки транспорта.

Идентичности FakeDNS хранятся в root-каталоге
`/private/var/run/tunneldeck-dns-<uid>` (0700), файлы `fake.v4`/`fake.v6` (0600).
Они содержат домены, считаются приватными, не входят в экспорт правил/журнал
и проверяются на владельца, права и ссылки. Модификация Xray сохраняет запись
до выдачи ответа; активность обновляется с ограничением частоты записи. Кеш
сохраняется между переподключениями; неактивные более 24 часов записи могут
удаляться, журнал уплотняется после 8 МБ. Пул ограничен 32768 идентичностями на
семейство. При заполнении активными записями выдаётся пустой DNS-ответ, без
перехода к реальным ответам, который мог бы обойти доменные правила.
Системный DNS-кеш очищается при смене сети. После выключения VPN приложения,
игнорирующие DNS TTL и сохраняющие синтетические адреса сами, могут потребовать
повторного запроса DNS или перезапуска; принудительно закрывать их TunnelDeck
не пытается.

Страны работают офлайн. `script/prepare_geoip.py` проверяет SHA-256 закреплённого
DB-IP Lite 2026-10 и создаёт `Runtime/geoip/geoip.dat` для Xray и `countries.bin`
для локального объяснения правил. Оба файла получены из одних диапазонов;
lookup индекс отображается в память и ищется бинарным поиском. Версия, хеши,
источник и атрибуция CC BY 4.0 включены в manifest/лицензии. Обновление базы
выполняется вместе с выпуском приложения, фоновой подписки нет.

Ограничения и границы:

- Общая схема не расширяет AllowedIPs/доступ сервера, не добавляет поддержку
  UDP/IPv6 протоколу, который её не предоставляет, и не делает fallback напрямую.
- Loopback, on-link LAN и более специфичные существующие системные маршруты не
  перезаписываются. Правила действуют на захваченные TCP/UDP-потоки; ICMP не
  реализован. Конфликт capture-маршрутов с другим VPN считается ошибкой.
- Выбор первого bootstrap IP не является полноценным перебором всех A/AAAA.
- Сон, смена физической сети, SIGKILL helper и совместная работа со сторонними
  VPN пока не подтверждены новой полной live-серией. Восстановление при штатной
  остановке реализовано; новая схема не заявляется kill switch.

## 7. Что учитывать при дальнейших изменениях

- Изменения движка, bootstrap resolution, bypass-маршрутов, SNI и TLS-профиля
  проверять вместе: успешный handshake вне туннеля не исключает петлю маршрутизации.
- Сохранять разделение уровней проверки: импорт, парсер движка, серверный
  handshake/авторизация, готовность сети, передача данных.
- При обновлении Xray переносить patch осознанно, запускать офлайн ClientHello
  tests и повторять SOCKS-проверку и полный VPN с DNS и отключением.
- Обновлять manifest, закреплённые SHA, сведения о модификациях и лицензии
  вместе с runtime. Не заменять изменённый core официальным бинарником без patch:
  имя `tunneldeck_safari15_5` в upstream отсутствует.
- Новые протоколы в whitelist подтверждать отдельной проверкой их Endpoint,
  обходных маршрутов и настоящего обмена с сервером.

Актуальное поведение определяют исходники приложения, закреплённый runtime,
его patch и воспроизводимые проверки.

## 10. Доменные исключения и Chrome, 16.10.2026

Проверки: 69/69 XCTest, все четыре сценария `routing_smoke.py`, сборка и
проверка подписи debug app bundle. Интеграционная проверка использует
эфемерный локальный TLS-сертификат: проверяет прямой/VPN/запрещённый выход
по Host/SNI при реальном IP, сохранение исходного IPv6-назначения при DNS-ответе
IPv4, домен и поддомен через FakeDNS с корневой точкой, приоритет известной
FakeDNS-идентичности над несовпадающим HTTP Host и сохранность после рестарта.
Синтетические проверки не меняют системную сеть и не подтверждают новый
удалённый VPN-handshake. Поставляемый Xray и его manifest не изменены.

Live-проверка итоговой сборки в AWG-сеансе на текущем Mac: получен handshake;
в Chrome при включённом VPN 2ip.io показал тот же выход, что перед подключением.
Дополнительно три независимых HTTPS-соединения к 2ip.io подтвердили совпадение
выхода системного запроса с явным `--resolve` на FakeDNS-адрес и выхода сокета,
привязанного к физическому интерфейсу с настоящим DNS-адресом. Принудительный
запрос через `td-probe` получил другой VPN-выход. Восемь параллельных HTTPS-проб
через VPN к example.com дали HTTP 200 (8/8). Адреса выходов не публикуются.

В предыдущем сеансе пользователь зафиксировал AWG `sendmsg: network is unreachable`
и вторичные ошибки DNS pipe. В повторном сеансе маршрут до VPN-сервера указывает
на физический интерфейс; после перечисленных запросов таких ошибок в журнале
нет. Причина первого сбоя не установлена; изменение доменных правил не заявляется
отдельным исправлением этой ошибки AWG. Повторное отключение, другие сети и
live-совместимость OpenConnect/Xray этой серией не проверены.

## 11. Исправление системной HTTPS-пробы Xray, 16.10.2026

В исходном журнале Xray запускался и принудительная SOCKS-проба получала
успешный HTTPS-ответ, но следующая проверка через системный TUN завершалась
ошибкой. Причина воспроизведена локально: после распознавания TLS SNI
`IPOnDemand` использовал DNS-адрес имени вместо служебного `198.18.0.3` при
сопоставлении правила моста. Прежний smoke отправлял HTTP с IP в Host и
не проверял настоящий TLS ClientHello, поэтому пропускал регрессию.

В `TunnelDeck.4` добавлено описанное в разделе 4.5 узкое исключение dispatcher.
Профиль REALITY, ключи, проверка сертификата и правила обычного трафика не
изменены. Версия движка, patch, исходники тестов, лицензия и manifest обновлены
согласованно. Две сборки из свежих каталогов закреплённого исходного архива
дали одинаковый SHA-256; проверка release pins прошла.

Проверки итогового изменения:

- Новый TLS-сценарий `routing_smoke.py` воспроизвёл ошибку на `TunnelDeck.3`.
  На `TunnelDeck.4` прошли все четыре сочетания native/proxy/страна/default,
  включая TLS-пробу с обычным, прямым, запрещённым и VPN-именем. Сохранились
  проверки HTTP/TLS-маршрутизации обычных адресов, TCP/UDP/IPv6, FakeDNS,
  приоритета идентичности, реального DNS и рестарта. Это локальные проверки
  без изменения системной сети и без удалённого VPN-handshake.
- Сборочные Go-тесты ClientHello, FakeDNS, proxy/dns и новый dispatcher-тест
  прошли. Последний проверяет HTTP/TLS и границы исключения: другой IP,
  FakeDNS-IP, порт, inbound, UDP и IPv6 сохраняют прежнее поведение.
- Приложение собрано и запущено через `build_and_run.sh --verify` с
  `DEVELOPER_DIR=/Library/Developer/CommandLineTools` и
  `SDKROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk`.
  Подпись bundle проверена; `engine_smoke.py` прошёл на подписанных копиях
  движков из приложения.
- В реальном Xray-сеансе итоговой сборки UI подтвердил HTTPS через VPN-канал
  и системный TUN; маршрут к служебному адресу шёл через `utun300`.
  Восемь параллельных обычных системных HTTPS-запросов к example.com получили
  HTTP 200 (8/8). Это подтверждённая передача данных в проверенном сеансе;
  новая серия отключения/восстановления сети и live OpenConnect/AWG не проводилась.

Полный Swift-набор в этой серии не выполнен: текущий CLT-комплект не содержит
XCTest. `network_configuration_smoke.py` также не выполнился, поскольку новый
Swift build engine размещает объекты не в ожидаемом fixture каталоге
`TunnelCore.build`. Сетевой helper этим исправлением не изменялся. SDK 27
из CLT дополнительно не предоставляет нужный SwiftUI macro plugin, поэтому
для успешной сборки интерфейса использован установленный SDK 26.5.

Поддерживаются русский и `en-US` с настройкой «Как в системе» / «Русский» /
«English (United States)». Swift suite прошёл 84/84 теста. Проверены основной
